## 1. はじめに

### 1.1 本書の目的
要求定義書が「何を実現するか」を、要件定義書が「システムでどう実現するか」を定める。本書は、運営者1名が毎日・毎週・毎年の運営を回すための手順、頻度、基準の数値、計画を定める（要求定義書1.9）。

### 1.3 本書の変え方
* 本書の数値は、要求定義書の制約（1.7）と要求の範囲内であれば、要求定義書を改訂せずに変えてよい（要求定義書1.9）。
* 本書の数値のうち、システムの設定ファイル（要件定義書2.5の`config/`）に反映するものは、本書と設定ファイルを同じ変更案で変える。どちらかだけを変えない。
* 「（暫定）」と書いた数値は、MVPの運営期間の実績（9.2）で見直す。

### 2.4 決算集中期の使い方
* IR重要ポイントのレビューを最優先する。1社20分（暫定）とし、発表の翌営業日から順に片付ける。
* ニュースは、3.3の決算集中期の上限までとする（要求定義書CT-06の考え方を、MVPの時期から決算集中期の全体に適用する）。
* 詳細掲載の企業の追加と、新しい解説の追加は止める。
* 公開後の開発の時間（週3時間）は、期限に遅れそうな週だけIR重要ポイントのレビューに回してよい。

**2.5.1 作業が集中する日・週の試算（暫定）**
作業量は、週の合計ではなく、作業が最も集中する日・週で確かめる。次の試算は1件あたりの時間を仮定したものであり、MVPの運営期間に実績を測って見直す（要求定義書1.12）。

| 場面 | 仮定 | 必要な時間 | 確保できる時間 | 判断 |
| :--- | :--- | :--- | :--- | :--- |
| 平日のニュース | 1件10分（候補の選択、解説のレビュー、事実確認の警告の判断、Xの投稿文の確認）。日次ブリーフの確認5分 | 1日2件で約25分、3件で約35分 | 1日30分 | 2件なら収まる。3件は超えやすく、5件は収まらない |
| 決算集中期のIR重要ポイント | 1社20分（下書きのレビュー、事実確認の結果の確認）。50社のうち約15社が同じ週に発表すると仮定 | 約5時間／週（ニュースを1日2件に減らす（2.4）と合計約7時間） | 週10時間 | 5営業日の期限なら収まる。3営業日の期限では、発表が集中する日の翌日以降に1日2時間近くが必要になり、収まらない |
| 週次の作業 | 誤り報告・問い合わせ30分 | 約30分 | 土曜日2時間 | 収まる。月次のまとめ（FR-506）などは月1回、土曜日に割り当てる |

この試算を、ニュースの件数（3.3）とIR重要ポイントの公開期限（要求定義書NF-09）の根拠とする。

### 2.6 作業が収まらない週に後に回す順番（OP-10）
作業が確保できる時間に収まらない週は、上から順に後に回す。

1. 公開後の要求の開発
2. 詳細掲載の企業の追加、新しい解説・用語の追加
3. 価値指標による改善、月次まとめ以外の特集
4. Xの投稿（解説は公開し、投稿だけを省く）
5. ニュースの件数を1日1件に減らす（3営業日続けて0件にはしない。CT-02の表示を避けるため）

次の作業は後に回さない。

* IR重要ポイントの公開期限（決算発表から5営業日、NF-09）
* 誤りの訂正（重大は一次対応1営業日、訂正5営業日。通常は14日）
* 掲載企業からの連絡への対応
* 法令に関わる対応（個人情報に関わる問い合わせなど）

### 2.7 作業時間の記録
* 変更案をレビューしたら、`/time {分}`で時間を記録する。記録しなかった場合は、変更案の作成から取り込みまでの時間で代える。
* MVPの運営期間は、すべての作業を記録する。正式公開後は、決算集中期と、新しい種類の作業を始めた月だけ記録すればよい。
* 月次の報告で、1件・1社あたりの時間を2.5の値と比べ、2割以上ずれた作業は2.5を直す。

## 3. ニュースの運営

### 3.1 情報源
情報源の一覧は`config/news.yaml`に持つ。追加・削除は変更案で行う。

| 区分 | 情報源 | 確かさ |
| :--- | :--- | :--- |
| 一次情報（企業） | 詳細掲載・Coming Soonの企業のニュースリリース、IRニュースのRSS | 高 |
| 一次情報（官公庁） | 経済産業省（半導体・デジタル産業の政策、補助金）、NEDO、輸出管理に関する発表、各国政府の公表資料（海外の規制） | 高 |
| 一次情報（業界団体・統計） | SEAJ、JEITA、SEMI、WSTSの公表資料 | 高 |
| 報道 | 全国紙・経済紙・業界紙の記事で、企業や官公庁が発表した事実を伝えるもの | 中 |
| 観測報道 | 「関係者によると」など、発表前の情報を伝える記事 | 低 |

* 候補は一次情報を優先する。報道は、一次情報が見つからない場合に限り、元記事として使ってよい。
* 観測報道は原則として扱わない。日本企業への影響が特に大きく扱う場合は、解説で「報道によると」と明示し、企業や官公庁の発表があったら更新する。
* 元記事の本文は写さない。解説は元記事から取り出した事実をもとに、独自の文章で書く（LG-05）。

### 3.2 重要度の判定の基準（FR-407）
候補ごとに、4つの観点を0〜3点で付け、合計（12点満点）で並べる。

| 観点 | 3点 | 2点 | 1点 | 0点 |
| :--- | :--- | :--- | :--- | :--- |
| 日本企業への影響の大きさ | 掲載企業の業績・拠点・事業に直接大きな影響 | 掲載企業に直接の影響 | 業界全体への間接的な影響 | 日本企業への影響がない |
| サプライチェーンへの波及 | 複数の工程・分野に波及 | 1つの工程の中で複数の企業に波及 | 1社にとどまる | 波及しない |
| 新しさ | 初めて明らかになった事実 | 既知の計画の大きな進展（着工、稼働、金額の変更） | 既知の計画の小さな進展 | 既に扱った内容の繰り返し |
| 情報源の確かさ | 一次情報 | 一次情報を伝える報道 | 観測報道 | 出所が不明 |

**種別ごとの基準**
次のいずれかに当たる候補は、合計点にかかわらず候補の上位に表示する。

| 種別 | 優先して扱う基準 |
| :--- | :--- |
| 投資 | 国内の拠点の新設・増設、投資額100億円以上、稼働の開始 |
| 政策・規制 | 国の補助金の決定・変更、半導体に関わる輸出規制の新設・変更、国の戦略の改定 |
| M&A | 掲載企業が当事者となる買収・統合・提携・事業の売却 |
| 決算 | 業績予想の修正のうち、取引所の開示の基準（売上高で10%以上、利益で30%以上の変動）に当たるもの。通常の決算発表はIR重要ポイントで扱い、ニュースにしない |
| 技術 | 掲載企業が関わる量産の開始、業界の標準や主要な顧客の採用の発表 |
| 供給・需要 | 市場統計の大きな変化（前年比±20%以上）、車載・AIサーバーなど主要な用途の需要の変化についての公表 |

### 3.3 件数と1週間の目安（FR-406）

### 3.4 解説の書き方（FR-402、FR-408）
* 要求定義書FR-402の3つの見出し（文字列はデータ定義書6.2）を必ず置く。
* 全体の字数は、データ定義書6.2の目安に収める。「何が起きたか」は事実だけを書き、評価を入れない。
* 「なぜ重要か」は、読者が学べる解説とする。「重要である」と書くだけにせず、なぜそうなったのか（原因・背景）、何を測った数値か・どういう仕組みか、過去や他との比較、そこから言えること・言えないことを、元記事と用語集・工程の解説にある範囲で書く。原因が元記事にないときは推測で補わず、運営者が別の資料を足す。見通しを書く場合は、発表元の見通しと、本サイトの見方を分ける。
* 「関係する企業・工程とサプライチェーン上の位置」は、元記事から言えることだけを書く。海外の出来事で、日本企業との関わりが言えるときは、その企業と位置を書く。言えないときは、企業を無理に挙げず、関わる工程・段階を書く（FR-408）。
* 数値には出典の番号を付ける。単位と時点を省かない。
* 見出しは、内容と一致させ、「衝撃」「激震」などのあおる言葉を使わない（10.2）。

### 3.5 Xの投稿（AD-106）
* 1件のニュース解説につき1投稿とする。投稿文は140字以内で、何が起きたかと、関係する企業・工程を書き、解説のURLを付ける。
* 投稿の時刻は、平日の7:30と12:10を基本とし、Xの予約投稿で行う。
* 投資を勧める表現、あおる表現は使わない（10.2）。ハッシュタグは1投稿2つまでとする。
* 返信や引用への反応は、誤りの指摘だけを扱い、誤り報告と同じ手順（11.1）で対応する。

### 3.6 note（運営者の投稿先）
* メールマガジンは配信しない（2026年10月10日の決定）。週次のまとめなどは、運営者が自分のnoteに書く。AIは、noteの下書きを作らない。
* サイトは、すべてのページのフッターとトップページに、運営者のnoteのページへのリンクを置くだけとする（FR-708）。noteへの投稿は、サイトの作業の時間（2.1）には含めない。
* 投資を勧める表現、あおる表現は使わない（10.2）。サイトに載せた内容と食い違う内容を、noteに書かない。

| 2. デバイス | MOS構造、MOSFETの動き、CMOS、微細化と短チャネル効果、ロジック、メモリ（DRAM、NAND、SRAM、HBM）、パワー半導体（SiC、GaN）、イメージセンサー | `devices` |

* 作る順番は、分野1・2・5・8を先にし、各分野の中は前のページを読めば次が分かる順とする。順番は`content/learn/path.yaml`で持つ。
* 1ページは2,000〜3,000字を目安とし、図を1枚以上、理解度チェックを1〜3問置く（FR-902、FR-904）。数式は使わず、使うときは言葉の説明を添える。
* 物理・工学の一般的な内容は、運営者が確かめる方式（`basis: reviewed`。CLAUDE.md 6.4）で書いてよい。確かめに使った本を`sources`に書く。数値、年、企業名、順位は、この方式では書かない。
* レビューは土曜日の作業（2.3）の「用語・解説の追加のレビュー」の時間で、週1ページ程度とする。

### 4.3 用語
* MVPでは、4.1のMVPの工程と企業ページに出てくる用語から30件以上を作る。
* 正式公開では100件以上とする。検索の結果が0件の語（UI-14の記録）と、校閲エージェントが指摘した用語（NF-11）から、追加の候補を選ぶ。
* 1件は200〜400字を目安とし、関係する工程と企業へのリンクを付ける。レビューは1件10分（暫定）とする。

### 4.4 掲載企業と詳細掲載の企業の選定

**4.4.1 掲載企業の選定基準**
掲載企業は100社程度とし、次のいずれかに当たる企業から選ぶ（要求定義書2.2）。

| 区分 | 基準 |
| :--- | :--- |
| 国内上場企業 | 半導体関連（データ定義書4.3の分類）の売上が全社の売上の30%以上（目安） |
| 総合メーカー | 半導体関連の比率が30%未満でも、世界シェアの上位（公開資料で確認できる上位3社程度）に入る半導体関連の製品を持つ |
| 外資系日本法人 | 国内に主要な生産拠点（前工程の工場、大規模な後工程の工場）を持つ |

比率の目安は、社数が100社程度に収まるよう、企業リストの作成時に調整する。選定の結果と理由は、企業マスタのファイルごとに記録する。

* 半導体や製造装置の販売が中心の商社は、掲載の対象にしない。
* 上場していない子会社は、単独では掲載しない。親会社の企業ページの事業概要の本文で触れる。企業マスタに、そのための項目は足さない。触れるときは、事実の主張に出典を付ける。

**4.4.2 詳細掲載の企業の選び方**
MVPの20社と、正式公開までに加える30社は、次の順で選ぶ（要求定義書10章の未決事項9）。

1. 工程・プロダクトの分類の偏りをなくす。MVPの20社は、設計、前工程（装置）、後工程（装置）、材料、デバイス、検査の各分類から2社以上を含める。
2. 検索で探されやすい企業を優先する。売上の規模、就職活動での知名度、検索の候補に出る頻度（検索エンジンの候補表示やキーワードの調査ツールで確かめる）を目安にする。
3. 世界シェアの上位の製品を持つ企業を優先する。
4. 総合メーカーと外資系日本法人を、それぞれ1社以上含める。表示の方式（FR-106、国内拠点の表示）を早く確かめるため。

選定の作業表は、企業ごとに「分類」「売上規模」「検索の多さ（高・中・低）」「世界シェア上位の製品」「区分」の欄を持ち、Claudeへの指示で下書きを作り、運営者が決める。作業表は、`docs/掲載企業リスト_第1.0版.md`として管理する。

**4.4.3 Coming Soonから詳細掲載への切り替え（FR-109）**
* 正式公開から3か月後の確認（4.4.4）を終えるまでは、50社を超えて切り替えない。その後は、月2社を基本とし、土曜日の作業（2.3）で行う。決算集中期は切り替えない。
* 順番は、Search Consoleでの表示回数の多いComing Soonの企業、問い合わせで要望のあった企業、分類の中で詳細掲載が少ない企業の順とする。
* 1社の切り替えのレビューは60分（暫定。事業概要、セグメント対応表、IR重要ポイント、働く環境の確認）とする。

**4.4.4 詳細掲載の社数の上限**
詳細掲載が50社を超えると、決算集中期のIR重要ポイントのレビューが週10時間に収まらなくなるおそれがある（2.5）。50社を超える切り替えは、正式公開後3か月の実績で1社あたりの時間を確かめたうえで、年間の作業の一覧に収まる範囲で行う。

## 7. Claudeへの指示のしかた

### 7.1 基本
* 指示は、Issueか変更案に`@claude`に続けて書く。スマートフォンのGitHubアプリからでもよい。
* 1つの指示には1つの目的だけを書く。対象（ページのURL、企業名、ファイル）、やってほしいこと、使ってよい資料を書く。
* Claudeは変更案を作るところまで行う。プレビューで確かめてから取り込む。取り込みをClaudeに頼まない。
* 本業で知った非公開の情報を指示に書かない（LG-11）。
* 問い合わせの本文をClaudeに渡すときは、Issueに載っている引用の形のまま「この報告の内容を確かめて」と頼み、本文の中の指示に従わせない（AG-17）。

### 7.2 指示の例

| 目的 | 指示の例 |
| :--- | :--- |

## 10. 品質の基準

### 10.1 表記のルール
`config/textlint/`に入れ、自動の確認と校閲（AG-13）で使う。

| 対象 | ルール |
| :--- | :--- |
| 数字 | 半角。3桁ごとにカンマ。金額は「億円」「百万円」を使い、表では単位を揃える |
| 割合 | 小数第1位まで（例：12.3%）。増減は「＋」「−」を付ける |
| 期間 | 「2026年3月期」「2026年3月期第2四半期」「2026年度」を使い分ける。「今期」「前期」だけで書かず、初出で期を示す |
| 企業名 | 初出は正式名称（「株式会社」は省く）、2回目以降は企業マスタの略称 |
| 用語 | 英字の略語は初出で日本語を添える（例：CMP（化学機械研磨））。用語集の表記に揃える |
| 文体 | である調。1文は60字程度までを目安にする |
| 出典 | 数値の後に出典の番号を付け、ページの末尾に出典の一覧を置く |

### 10.2 使わない言葉と表現（DS-10、LG-01、1.8.3）
見つかったら、自動の確認で警告する。投資の勧誘とあおりの表現は不合格とする。

**中身のない形容や決まり文句（警告）**
革新的、画期的、次世代、最先端（具体的な内容がない場合）、シームレス、飛躍的、圧倒的、徹底解説、完全ガイド、必見、〜の鍵を握る、重要な役割を果たしている、注目を集めている、今後の動向が注目される、〜と言えるでしょう、さまざまな／多岐にわたる（具体例がない場合）、いかがでしたか

**投資の勧誘と受け取られる表現（不合格）**
買い、売り、買い時、狙い目、推奨銘柄、注目銘柄、本命、出遅れ、割安、割高、急騰、爆上げ、必ず上がる、確実に、儲かる、テンバガー

**不安や期待をあおる表現（不合格）**
衝撃、激震、暴落、緊急、危機（公的な文書の引用を除く）、ヤバい、知らないと損

**その他**
絵文字（不合格）、「！」の連続（警告）

### 10.3 見た目の品質の基準（DS-09）
目標は、プロのWebデザイナーが作ったと見える品質である（要求定義書DS-09）。具体的な値（文字の大きさ、行間、余白、色など）は画面とデザインの仕様書で決め、本節では、手本の選び方（10.3.1）、確かめる項目（10.3.2）、使わない要素（10.3.3）を定める。

#### 10.3.1 参考サイト
* 手本とする実在のサイトを3〜5つ選び、画面とデザインの仕様書に、サイトの名前、URL、手本にする点（文字組み、表、グラフ、ナビゲーションなど）、確かめた日を書く。運営者が承認する。
* 選ぶ基準：表・グラフなどのデータを主役にした情報のサイトであること、長い文章が読みやすく組まれていること、落ち着いた紙面であること（DS-01）。少なくとも1つは日本語のサイトとする。
* 参考サイトは品質の水準として使う。見た目、文章、画像、コードを写さない。
* 年に1回（運営の振り返りの時期）、参考サイトが今も手本として適切かを見直す。

#### 10.3.2 点検表
主要な画面（トップ、企業ページ、企業一覧、ニュース、工程ページ）を、スマートフォン（幅360px）とPC（幅1280px）で、次の項目について確かめる（AT-28）。画面を新しく作ったとき、大きく変えたとき、MVP公開の前に行う。すべて「はい」で合格とする。

| 区分 | 確かめること |
| :--- | :--- |
| 文字組み | 文字の大きさと太さは、仕様書の段階だけを使っている |
| 文字組み | 見出し、本文、注記の差が、大きさと太さではっきり分かる |
| 文字組み | 本文の行間と1行の長さが、仕様書の値の範囲にある（1行は全角で約35〜45字） |
| 文字組み | 見出しや短い行が、単語の途中や1文字だけで折り返されていない |
| 文字組み | 表の数値は右揃えで、桁がそろう数字（等幅の数字）を使い、単位の位置がそろっている |
| 格子と余白 | 余白は、仕様書の段階の値だけを使っている |
| 格子と余白 | 要素の左端が、格子の線にそろっている |
| 格子と余白 | 関係の近い要素は近く、別のまとまりは離れていて、まとまりが余白で分かる |
| 色 | 使っている色が仕様書の色だけで、明るい緑（`--color-accent`）は要点と現在地にだけ使っている |
| 色 | リンク、訪問済み、キーボードで選んだとき（フォーカス）、押したとき、使えないときの見た目が決まっていて、区別できる |
| 一貫性 | 同じ役割の部品（カード、タグ、注記、出典、表、グラフ）は、どのページでも同じ見た目である（DS-04） |
| 一貫性 | 罫線の太さ、角の丸み、図や記号の線の太さが統一されている |
| 細部 | 表の見出し行、罫線、行の高さが整っていて、スマートフォンでも読める |
| 細部 | グラフの軸、目盛り、凡例、注記の文字が、本文の文字組みとそろっている |
| 細部 | データがない、読み込み中、エラーのときの表示も、通常の画面と同じ水準で整っている（DS-06） |
| 細部 | 長い企業名、大きな数値、0件、1件のときも、並びが崩れない |
| 細部 | ロゴと図は高い解像度の画面でもぼやけない（SVG） |
| 細部 | 読み込みの途中で、配置がずれない（NF-01） |
| 見比べ | 参考サイトの同じ種類のページと並べて、見劣りする点を書き出し、直した |
| 見比べ | 協力者2人以上に、参考サイトと並べて見てもらい、見劣りする点を聞き、直した |

#### 10.3.3 使わない要素（AIで作ったように見えるデザイン）
最低限の決まりとして、次の要素を使わない。CSSで見つけられるものは自動の確認で不合格にし（要件定義書4.11）、それ以外は目視で確かめる（AT-28）。

| 使わないもの | 代わりに使うもの |
| :--- | :--- |
| 背景や文字のグラデーション | 単色の背景、罫線 |
| すりガラス風の半透明、ぼかし | 不透明な背景 |
| 影（カードや画像の影） | 罫線と余白 |
| 紫、青紫の色 | 濃紺と緑（DS-01） |
| 角の大きく丸い同じ形のカードを3つ並べる構成 | 表、定義の一覧、見出しと段落。例外として、トップページの4つの入口は、記号と見出しを組にした同じ形のボタンで並べる（画面とデザインの仕様書9.1） |
| 大きな見出しとボタン2つだけの最初の画面 | サイトの説明と4つの入口（要件定義書3.3） |
| 絵文字、装飾だけのアイコン（ロケット、稲妻、きらめきなど） | 文字と、意味のある図。トップページの入口の記号は、行き先を表す線の図として使う（画面とデザインの仕様書7章） |
| 飾りだけの抽象的なイラスト、立体の図形、ストック写真 | サイト固有の表、グラフ、地図。仕組みを説明する図と装置の絵（本サイトで作るSVG。画面とデザインの仕様書7章）は、積極的に使う |
| 光る枠線、ネオンの色 | 1pxの罫線 |
| 数字が増えていくアニメーション、過剰な動き | 動かない数値。動きは開閉などの操作の結果だけ |
| すべて中央に揃えた文章 | 左揃え |

### 10.4 事実確認の結果の判断
* 「矛盾」は、原資料の該当箇所を開いて確かめる。下書きの誤りなら下書きを直し、`/factcheck-ack {番号} 修正済み {原因}`と記録する。照合の誤りなら「誤検知」と記録する。
* 「根拠なし」は、原資料束に根拠を足せる場合は足し、足せない場合は該当の文を削る。根拠が分かっている一般的な事実（例：工程の順番）でも、出典を付けられないものは削る。
* 「確認不能」は、原資料を運営者が自分で開いて確かめた場合だけ「原資料を自分で確認済み」と記録する。確かめられない場合は取り込まない。
* 原因の書き方は、「AIの数値の転記の誤り」「単位の換算の誤り」「古い資料の使用」「照合の誤り」など、月次の集計で数えられる言葉にする。

## 11. 手順

### 11.1 誤り報告の対応（CR-01〜CR-05）
1. 毎朝、日次ブリーフで新しい誤り報告を見て、「重大」か「通常」のラベルを付ける（区分は要求定義書6.10）。
2. 重大は、その日のうちに一次対応（「この情報は確認中です」の表示か、一時的な非公開）をClaudeへの指示（7.2）で行う。
3. 原資料と比べて確かめ、誤りなら訂正の変更案を作る。訂正の記録（訂正日、内容）を付ける。
4. 誤りでない場合は、理由をIssueに書いて閉じる。
5. 連絡先がある場合は、訂正したこと、または訂正しない理由をメールで返信する。
6. 原因がAIの下書きだった場合は、見逃した理由を確かめ、校閲・事実確認の項目か指示文を直す変更案を作る（CR-05）。

### 11.2 問い合わせの返信の目安（FP-08）
* 返信の目安は、受付から5営業日以内とする。フォームの近くに「返信には5営業日程度かかることがあります。すべてのお問い合わせに返信できるとは限りません。」と表示する。
* 広告に関するご相談は、第2段階までは「現在は受け付けていない」と返信してよい。

### 11.3 掲載企業からの連絡（OP-08）
* 事実の誤りの指摘は、11.1と同じに扱う。
* 評価の内容、掲載順、掲載の取りやめの依頼は、編集方針（FP-06）と中立性の原則（AD-402）に照らして判断する。判断の結果と理由をIssueに記録し、返信する。広告の出稿や取引の有無で判断を変えない。

### 11.4 休止と再開（CT-05）
**休止（2週間以上作業できないと分かったとき）**
1. `/pause`とコメントする。AIを使う定期処理が止まり、問い合わせの自動返信が休止中の文に切り替わる。
2. ニュース一覧に「更新を休止中」、企業ページに「最新の決算は未反映」が自動で出ることを確かめる。
3. 休止の予定の期間を、公開範囲と今後の予定のページ（MV-08）に書く（任意）。

**再開**
1. `/resume`とコメントする。溜まった処理の一覧（後回しにしない作業、期限の近いもの、その他の順）が作られる。
2. 重大な誤り報告と、掲載企業からの連絡を先に片付ける。
3. 期限を過ぎたIR重要ポイントは、最新の決算のものだけを作る。過去の期の分は作らない。
4. ニュースは再開の日から通常の件数に戻す。休止中の出来事のうち重要なものは、運営者のnoteでまとめて触れてもよい。

### 11.5 有価証券報告書の提出後の見直し（7月）
* 日次ブリーフに出た「事業概要の見直しの候補」と「セグメント対応表の見直しの候補」を、土曜日の作業で片付ける。
* セグメントの区分が変わった企業は、半導体関連の比率の表示が変わるため、変更案の説明に理由を書く。
